# Graphify 지식베이스 채팅/답변 및 문서 업로드 설계

작성일: 2026-04-10
문서 목적: 현재 Graphify 앱 위에 추가할 핵심 기능인 `지식베이스 기반 채팅/답변`과 `파일(문서) 업로드`의 제품 설계, 사용자 흐름, 유스케이스, 시스템 구조를 정의한다.
기준 상태: 현재 구현 기준으로 인증, 프로젝트/팀/권한 조회, 메타데이터 검색, 그래프 화면 기본 UI가 존재함

연계 문서:

- `docs/2026-04-10-knowledgebase-chat-wireframes.md`: 화면별 와이어프레임, 진입점, 상태, 상호작용 상세
- `docs/2026-04-10-knowledgebase-chat-handoff-and-next-steps.md`: 다음 세션용 요약과 후속 작업 계획

## 1. 배경

현재 앱은 아래 기능까지는 동작한다.

- 로그인/세션 유지
- 보호 라우트
- 프로젝트, 팀, 권한 조회
- 메타데이터 검색
- 그래프 UI 기본 구조

하지만 앱의 핵심 목표인 아래 기능은 아직 비어 있다.

- 지식베이스 기반 질문/답변
- 업로드한 문서를 기반으로 한 검색/답변
- 문서 업로드 후 분석 및 인덱싱

이 문서는 그 공백을 메우기 위한 실제 제품 설계 문서다.

## 2. 제품 목표

이 기능의 목적은 아래 두 가지다.

1. 사용자가 회사 문서, 설계 문서, 회의록, 운영 문서를 업로드할 수 있어야 한다.
2. 사용자가 업로드된 지식베이스를 바탕으로 질문하고, 근거가 포함된 답변을 받아야 한다.

핵심 원칙은 아래와 같다.

- 답변은 항상 근거 기반이어야 한다.
- 사용자는 어떤 문서에서 답이 왔는지 확인할 수 있어야 한다.
- 권한이 없는 문서는 검색/답변에 포함되면 안 된다.
- 업로드와 분석은 비동기 작업이어야 한다.
- 검색, 채팅, 문서, 프로젝트가 하나의 흐름으로 이어져야 한다.

## 3. 핵심 사용자 문제

현재 사용자는 아래 문제를 겪는다.

- 문서가 흩어져 있어서 필요한 정보를 빠르게 못 찾는다.
- 문서를 읽더라도 "결론만" 알고 싶을 때 시간이 오래 걸린다.
- 어떤 프로젝트/팀의 문서가 최신인지 판단하기 어렵다.
- 질문에 대한 답을 얻어도 출처를 다시 확인해야 한다.
- 권한에 따라 보여야 할 정보가 다르다.

이 설계의 목표는 아래 형태의 경험을 만드는 것이다.

- "이 프로젝트의 아키텍처 결정 이유가 뭐야?"
- "Sarah가 작성한 최근 권한 변경 문서 요약해줘"
- "업로드한 PDF에서 배포 절차만 정리해줘"
- "이 답변의 출처 문서 3개만 보여줘"

## 4. 기능 범위

## 4.1 MVP 범위

MVP에서 우선 구현할 기능은 아래와 같다.

- 프로젝트 단위 문서 업로드
- 업로드 후 분석 작업 생성
- 문서 텍스트 추출 및 청크 분할
- 문서 메타데이터 저장
- 프로젝트 범위 검색
- 채팅 입력
- 근거 포함 답변 생성
- 답변에 출처 문서/청크 표시
- 채팅 세션 저장
- 권한 기반 문서 필터링

## 4.2 확장 범위

MVP 이후 확장 기능은 아래와 같다.

- 이미지/PDF OCR 강화
- 그래프 기반 관계 추출과 답변 결합
- 벡터 검색(Qdrant/pgvector)
- 추천 질문
- 문서 버전 비교
- 채팅 답변을 그래프 탐색 화면으로 연결
- 인용된 문서 미리보기

## 5. 사용자 역할

현재 역할 체계를 그대로 사용한다.

- `admin`
- `editor`
- `viewer`

역할별 기대 행동은 아래와 같다.

- `admin`: 업로드, 답변 조회, 프로젝트 전체 범위 검색/질문
- `editor`: 자신이 접근 가능한 프로젝트 범위에서 업로드와 질문
- `viewer`: 읽기 전용 검색과 질문

## 6. 핵심 유스케이스

## 6.1 유스케이스 목록

### UC-01. 프로젝트 문서 업로드

- 행위자: admin, editor
- 목적: 프로젝트에 새 문서를 넣는다.
- 성공 조건: 문서가 저장되고 분석 작업이 생성된다.

### UC-02. 업로드 상태 확인

- 행위자: admin, editor
- 목적: 업로드가 처리 중인지 완료됐는지 본다.
- 성공 조건: 상태가 `PENDING`, `RUNNING`, `COMPLETED`, `FAILED` 중 하나로 보인다.

### UC-03. 프로젝트 범위 질문

- 행위자: admin, editor, viewer
- 목적: 특정 프로젝트의 지식베이스를 기준으로 질문한다.
- 성공 조건: 근거 포함 답변이 반환된다.

### UC-04. 워크스페이스 범위 질문

- 행위자: admin
- 목적: 여러 프로젝트를 가로질러 질문한다.
- 성공 조건: 권한이 있는 문서만 범위에 포함된다.

### UC-05. 후속 질문

- 행위자: admin, editor, viewer
- 목적: 직전 답변을 바탕으로 후속 질문한다.
- 성공 조건: 채팅 세션 문맥이 유지된다.

### UC-06. 답변 출처 검증

- 행위자: 모든 로그인 사용자
- 목적: 답변이 어떤 문서 조각에 기반했는지 확인한다.
- 성공 조건: 문서명, 프로젝트명, 발췌문, 위치 정보가 표시된다.

### UC-07. 업로드 실패 복구

- 행위자: admin, editor
- 목적: 파싱 실패/권한 문제/지원하지 않는 형식 문제를 확인하고 재시도한다.
- 성공 조건: 실패 원인이 보이고 다시 업로드할 수 있다.

## 7. 사용자 흐름

## 7.1 문서 업로드 흐름

```text
1. 사용자가 프로젝트 화면 또는 전용 업로드 화면으로 이동
2. "Upload documents" 버튼 클릭
3. 파일 선택 또는 드래그앤드롭
4. 업로드 대상 프로젝트 확인
5. 메타데이터 입력
   - 제목
   - 태그
   - 문서 유형
6. 업로드 요청 전송
7. 서버가 파일을 저장하고 graph_job 또는 ingestion_job 생성
8. 상태가 PENDING -> RUNNING -> COMPLETED/FAILED 로 변경
9. 완료 시 검색 및 채팅 답변 대상에 포함
```

## 7.2 질문/답변 흐름

```text
1. 사용자가 대시보드 또는 전용 chat 화면에서 질문 입력
2. 범위 선택
   - 현재 프로젝트
   - 현재 팀
   - 전체 워크스페이스
3. 서버가 권한 범위를 계산
4. 검색기(retriever)가 관련 문서/청크/메타데이터를 수집
5. 응답기(generator)가 근거 기반 답변 생성
6. 답변과 함께 출처 목록 반환
7. 사용자는 후속 질문 또는 출처 열람
```

## 7.3 후속 질문 흐름

```text
1. 사용자가 기존 채팅 세션 안에서 추가 질문
2. 서버가 직전 대화 맥락 + 현재 검색 결과를 함께 사용
3. 문맥 오염 방지를 위해 세션 범위를 유지
4. 답변과 출처를 다시 반환
```

## 7.4 실패 흐름

```text
업로드 실패:
1. 업로드 요청
2. 파일 형식 오류 또는 파싱 실패
3. 상태 FAILED
4. 사용자에게 원인 표시
5. 재시도 또는 다른 형식 업로드

답변 실패:
1. 질문 입력
2. 검색 결과 부족 또는 처리 오류
3. 사용자에게 "충분한 근거 없음" 또는 오류 메시지 표시
4. 관련 문서 업로드/검색 제안
```

## 8. 제안 화면 구조

## 8.1 옵션 A: 기존 화면 확장

기존 앱 흐름을 덜 깨는 방식이다.

- 대시보드 중앙 `Ask Graphify...` 입력을 실제 채팅 진입점으로 사용
- 프로젝트 화면에 `Upload documents` 버튼 추가
- 검색 화면을 `검색 + 답변 준비 화면`으로 확장

장점:

- 현재 구조를 많이 바꾸지 않는다.
- 빠르게 MVP를 만들 수 있다.

단점:

- 채팅 경험이 분산될 수 있다.

## 8.2 옵션 B: 전용 Chat 화면 추가

추천안은 이쪽이다.

새 라우트:

- `/chat`
- `/chat/:sessionId`
- `/projects/:projectId/documents`

구성:

- 좌측: 세션 목록
- 중앙: 대화 영역
- 우측: 답변 근거/출처 패널

장점:

- 채팅/답변이 앱의 중심 기능으로 드러난다.
- 후속 질문과 출처 패널을 자연스럽게 붙일 수 있다.

단점:

- 초기 구현 범위가 조금 더 크다.

## 10. 백엔드 설계

## 10.1 핵심 개념

채팅/업로드 기능은 아래 4개 레이어로 나뉜다.

1. 파일 수집
2. 문서 분석/청크화
3. 검색/재순위화
4. 답변 생성

## 10.2 제안 API

### 문서 업로드

```text
POST   /projects/{projectId}/documents
GET    /projects/{projectId}/documents
GET    /documents/{documentId}
DELETE /documents/{documentId}
GET    /documents/{documentId}/chunks
```

### 업로드/분석 상태

```text
POST   /projects/{projectId}/jobs?source=UPLOAD
GET    /projects/{projectId}/jobs
GET    /jobs/{jobId}
PUT    /jobs/{jobId}/status
PUT    /jobs/{jobId}/error
```

현재 `GraphJobController`가 메모리 기반 stub으로 존재하므로, MVP에서는 이 흐름을 실제 DB 기반으로 교체하는 것이 맞다.

### 채팅/답변

```text
POST   /chat/sessions
GET    /chat/sessions
GET    /chat/sessions/{sessionId}
POST   /chat/sessions/{sessionId}/messages
GET    /chat/sessions/{sessionId}/messages
POST   /chat/answer
```

권장안:

- 단건 답변은 `POST /chat/answer`
- 대화 저장형은 `POST /chat/sessions/{sessionId}/messages`

## 10.3 답변 파이프라인

```text
1. 질문 수신
2. 사용자 권한 범위 계산
3. 범위 내 프로젝트/문서/청크 필터링
4. 검색
   - 키워드 검색
   - 메타데이터 검색
   - 그래프 관계 검색
   - 향후 벡터 검색
5. 상위 근거 청크 선택
6. LLM에 질문 + 근거 전달
7. 답변 생성
8. 인용/출처와 함께 저장 및 반환
```

## 11.2 기존 모델과의 연결

현재 `graph_jobs`는 `source=UPLOAD`를 이미 허용한다.

따라서 첫 단계 설계는 아래가 가장 자연스럽다.

- 문서 업로드 시 `documents` 레코드 생성
- 동시에 `graph_jobs`에 `source=UPLOAD` 작업 생성
- 분석 완료 후 `graphs` 또는 문서 인덱스 갱신

즉, 업로드 파이프라인은 기존 `graph_jobs`와 연결하고, 문서 자체 메타데이터는 `documents`가 담당한다.

## 12. 검색 전략

## 12.1 MVP 검색 전략

MVP는 아래 조합으로 충분하다.

- PostgreSQL 메타데이터 검색
- 청크 단위 full-text 검색
- 프로젝트/팀/권한 기반 필터링

이 단계에서 중요한 것은 답변 품질보다 "근거가 있는 답변"과 "권한 제어"다.

## 12.2 확장 검색 전략

다음 단계에서는 하이브리드 검색으로 간다.

- BM25/full-text
- graph neighborhood retrieval
- vector similarity
- reranker

이 부분은 기존 [PHASE2_VECTORDB_EXPANSION.md](/mnt/c/workspaceRND/graphify/graphify/docs/PHASE2_VECTORDB_EXPANSION.md)에 연결된다.

## 13. 권한 설계

권한은 검색 전에 적용해야 한다.

원칙:

- 권한 없는 문서는 검색 후보에 포함하지 않는다.
- 답변에 권한 없는 문서가 인용되면 안 된다.
- 세션 범위보다 더 넓은 문서는 자동 제외한다.

권한 체크 순서:

1. 사용자 인증 확인
2. 세션 범위 계산
3. 프로젝트 접근 권한 확인
4. 문서 접근 가능 목록 생성
5. 그 문서만 검색/인용 가능

## 14. 대표 user flow

## 14.1 프로젝트 문서 업로드 후 질문

```text
1. 사용자가 Projects 화면 진입
2. 특정 프로젝트 선택
3. "Upload documents" 클릭
4. PDF/Markdown/Docx 업로드
5. 상태가 READY가 될 때까지 대기
6. Chat 화면에서 질문
   "이 문서 기준으로 승인 절차만 요약해줘"
7. 답변 수신
8. 출처 문서와 인용문 확인
```

## 14.2 검색 후 채팅으로 확장

```text
1. 사용자가 Search 화면에서 "권한" 검색
2. 관련 프로젝트/문서 후보 확인
3. "이 내용으로 질문하기" 클릭
4. Chat 화면으로 이동
5. 질문 자동 주입 또는 문맥 전달
6. 답변과 출처 표시
```

## 14.3 팀 범위 질의

```text
1. 사용자가 Team 문맥 안에서 질문
2. 시스템이 팀에 속한 프로젝트 문서만 검색
3. 답변 반환
4. 문서가 부족하면 업로드 유도
```

## 15. 대표 질문 예시

이 기능이 지원해야 할 질문은 아래 범주를 커버해야 한다.

### 요약형

- "이 프로젝트의 배포 절차를 요약해줘"
- "최근 업로드된 운영 문서 핵심만 정리해줘"

### 사실 확인형

- "권한 변경 승인자는 누구야?"
- "이 문서에서 SLA 기준이 몇 분으로 적혀 있어?"

### 비교형

- "아키텍처 v1과 v2의 차이가 뭐야?"
- "두 프로젝트의 인증 흐름 차이를 알려줘"

### 절차형

- "새 팀원을 온보딩하려면 어떤 단계가 필요해?"
- "장애 발생 시 대응 순서를 알려줘"

### 탐색형

- "이 주제와 관련된 문서를 더 보여줘"
- "이 답변의 출처 문서만 따로 열람하고 싶어"

## 16. 비기능 요구사항

### 응답성

- 업로드 요청 응답: 1초 이내
- 질문 응답 시작: 3초 이내
- 검색 결과: 1초 내외

### 신뢰성

- 답변에 최소 1개 이상의 근거가 있어야 한다.
- 근거 부족 시 추측형 답변 대신 "근거 부족"을 우선한다.

### 보안

- 파일은 인증 사용자만 업로드 가능
- 권한 범위 밖 문서는 검색 후보 제외
- 민감 문서는 세션/프로젝트 범위를 벗어나 인용 금지

### 감사 가능성

- 누가 어떤 문서를 업로드했는지 남겨야 한다.
- 누가 어떤 질문을 했는지 세션 단위로 남길 수 있어야 한다.

## 18. 현재 기준 권장 구현 방향

현재 앱 상태를 고려하면 아래 순서가 가장 현실적이다.

### 1단계

- 프로젝트에 문서 업로드
- 업로드 상태 표시
- 단건 질문/답변
- 출처 문서 표시

### 2단계

- 채팅 세션 저장
- 후속 질문
- 검색 결과에서 채팅 연결

### 3단계

- 그래프 추출 결합
- 벡터 검색 결합
- 고급 추천/탐색

## 19. 결론

이 앱의 핵심은 단순 조회 UI가 아니라 아래 경험으로 수렴해야 한다.

- 문서를 프로젝트에 넣는다.
- 시스템이 문서를 분석해 지식베이스로 만든다.
- 사용자가 질문한다.
- 시스템이 권한 범위 안에서 근거 기반 답변을 준다.
- 사용자는 출처를 검증하고 후속 질문을 이어간다.

즉, 최종 제품 경험은 `업로드 -> 분석 -> 검색 -> 답변 -> 검증 -> 후속 질문`의 연속된 흐름이어야 한다.
